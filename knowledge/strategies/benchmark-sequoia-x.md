# 对标分析：Sequoia-X vs feishu-stock-monitor

- 对标项目: https://github.com/sngyai/Sequoia-X（6.8k stars，A股自动选股+飞书推送）
- 分析日期: 2026-09-09
- 结论: **选股扫描层对方更工程化（值得抄），AI/模型层我们独有（对方的空白）**

## 对方架构（提炼）

- 数据: baostock 全市场5200只，后复权日线，SQLite本地库，8进程增量更新
- 策略: 抽象基类 strategy/base.py + 6个选股策略（海龟/均线放量/旗形/涨停洗盘/跌停反包/RPS）
- 推送: 飞书webhook（与我们同类）
- 工程: pydantic-settings 配置、rich日志、hypothesis属性测试、uv/ruff
- 无回测、无LLM、无实时监测、无交互查询、无模型

## 差距清单（对方有、我们没有）

| # | 差距 | 影响 | 行动项 |
|---|------|------|--------|
| 1 | 策略抽象基类统一接口 | 策略可插拔、社区可贡献 | 我们的 RuleEngine 已有 Rule 协议，差距不大；但策略注册可学习其 base 模式 |
| 2 | 全市场数据本地化(SQLite增量) | 扫全池无需每次拉网 | 我们的 screener 每次实时拉腾讯源，300只需2-3分钟且依赖数据源状态 → **建议引入本地缓存层** |
| 3 | 工程规范(pydantic/rich/hypothesis) | 可维护性 | 可选升级，优先级低 |
| 4 | 并行(8进程)数据更新 | 速度 | 引入缓存层时一并考虑 |

## 我们的独有优势（对方没有）

1. **AI模型层**: ImprovedKMeans聚类在线匹配(离线训练+在线匹配两阶段) + TechnicalPatternRecognizer形态桥接——对方6个策略全是规则，无任何模型
2. **LLM解读层**: 信号自动生成解读卡片(带禁荐股约束+降级链路)
3. **交互查询**: @机器人个股体检(长连接无需公网)
4. **复盘闭环**: 多维表格信号流水+胜率回填设计(对方无回测)
5. **数据源冗余**: 腾讯→东财→akshare三级fallback(对方单源baostock)
6. **知识工程**: knowledge/三层记忆+skill化(训练有素的agent工作流)

## 行动决策与验收（2026-09-09）

### 已实施：本地全池数据层

已完成对差距 #2 的第一阶段闭环，采用“**收盘同步 → 纯本地筛选**”而非原先逐股边拉边筛：

- `stock_monitor/data/store.py`：固定 `daily + qfq` 口径的 SQLite 日线库；K线表带 `period/adjust/provider`，元数据表记录最后确认交易日、同步状态与错误；WAL + busy timeout 为受控并发做准备
- `stock_monitor/sync.py`：4线程并发网络抓取、主线程单写者落库，避免 SQLite 多写锁竞争
- `stock_monitor/screener.py`：`screen_local()` 批量读 SQLite 后执行规则，**不触发任何外部行情请求**；缓存缺失/不足的股票单独计数
- `main.py`：新增 `--sync-pool` 与 `--screen-local`；常驻收盘任务自动执行“同步 → 本地筛选”

首轮验收（25只沪深300样本）：4线程同步 **12.9秒**，纯本地筛选+飞书推送 **8.8秒**，同步成功25/25、本地可用25/25；19个测试通过。

### 已知局限与下一步

- 当前每只同步仍从行情源拉取近250根前复权日线，以正确刷新公司行动后的复权窗口；这是正确性优先的取舍，尚非“只拉一根当日bar”的网络最优方案
- 全池300只尚未完成首次预热，需在收盘后运行 `python -m stock_monitor.main --sync-pool --workers 4`；预热完成后再测全池端到端耗时
- 下一项对标行动是**海龟20日通道突破 + 量能 + MA60趋势过滤**（见对标审阅）；不与本轮数据工程混合实施
- P3 工程规范（Pydantic/Rich/Hypothesis/uv/ruff）仍低优先级
